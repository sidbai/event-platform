01 — Overview

The shape of it

One Next.js application, one Postgres database, deployed on managed infrastructure with near-zero DevOps. Not microservices — a modular monolith where each product area (events, teams, scrimmages, tournament ops, discussion, weekly, social) is a self-contained feature folder that shares one schema.

The product thesis from the discussion doc holds up technically: Event is the core object — a generic container, not a fixed list of types. A game, scrimmage, pickup run, tournament, watch party, meetup, or tryout is the same row with different modules switched on. That keeps the data model small and the surface area open-ended. King Juan Cup is the flagship Event, and moving it onto the platform is the forcing function that makes the tournament-ops features real rather than hypothetical.

The website is the event and community layer (browse, join, host, manage). Instagram is the discovery and distribution layer. The platform's job at the seam between them is to turn event data into shareable graphics and captions automatically — that pipeline is a first-class service, not an afterthought.

02 — Product model

Event is a generic container

A game, a scrimmage, a pickup run, a tournament, a watch party, a coaches' meetup, a club tryout, or something nobody has named yet — each is one row in events. The row does not hard-code behavior by type. It carries a kind (a label, editable without a deploy) and a set of modules it switches on.

Code branches on modules, never on the kind string. A new kind is a row in event_kinds (slug, label, icon, default modules) — the discovery UI gets a new filter and icon; the code paths stay finite.

The modules

moduleadds
fixtureone match between two sides → a single matches row
competitiondivisions, a schedule, and standings with a configurable tiebreaker order → many matches
rostera player list per team per event (name, birth year, gender), with min/max and eligibility rules

attendancean RSVP list at the person or team level → rsvps
registrationstructured signup: capacity, questions, optional fee → registrations
sessionsmultiple dated parts under one event (a week of camp)
broadcasta reference to an external match / stream being watched together
recurringa parent event with child event_occurrences

Two things cut across every kind:

  • Place & time — a venue with lat/lng, or location_type = online with a URL. Plus a start time. "This weekend near Bellevue" stays one indexed query for both the site and the Instagram pipeline.
  • Audience filters — age_group, gender, level, all optional, because a coaches' meetup has no age group and a watch party has no level.

Submissions and claims aren't separate tables. A community-submitted event is an events row with status = 'pending' until a moderator publishes it. A knockout fixture whose team isn't decided yet stores a home_placeholder like "Group A winner" until results resolve it — exactly what the current King Juan Cup schedule sheet does by hand.
04 — Community

Event discussion

Every event has a thread. Reading is public; posting takes a Google login. It is the coordination surface — "can we push kickoff to 4?", "still on in this rain?", "where do we park?", "great games today, are photos up?".

How it works

  • Polymorphic, one implementation. A discussions row attaches by (subject_type, subject_id). The event thread, team-page thread, and post comments are the same code.
  • Shallow threading. Top-level comments plus one level of replies. This is coordination, not a message board.
  • Organizer controls. The event's organizer can pin one comment (a field change, a weather call), lock the thread, and hide individual comments. Platform admins can do this anywhere.
  • Batched notifications. A new comment notifies the organizer immediately; everyone who commented, RSVP'd, or follows the event gets a once-a-day digest, opt-out per thread. No per-message email.
  • Public thread ≠ private negotiation. Accepting an opponent offer opens a private thread scoped to the two teams (Phase 2 messaging). The public event thread stays for parents and players.
  • Youth-safety by default. Real-identity accounts only (Google, no anonymous posts), an optional per-event "verified coaches only" mode, rate limiting, a report button, and an admin review queue.
  • No realtime yet. Server-render and revalidate on post. Add live updates only if match-day threads get busy enough to need them.

07 — Modules

Services to build

Not separate deployments — feature folders in one app (/features/events, /features/tournaments, …), each owning its routes, components, queries, and jobs.

P0

Event catalog & discovery

List + filter (kind, date, age, gender, level, format, location), event detail page, map view, "submit an event" form. The public heart of the site.

P0

Team directory & claim

Team pages, search, "this is my team" claim flow with lightweight verification, team member roles. Team is the long-term identity anchor.

P0

Scrimmage & opponent matching

Create an event with needs_opponent, browse open requests, send/accept offers. Coach-to-coach messaging comes later (P1).

P0

Tournament ops

Divisions, registration + roster (5–8 players, birth-year rules), schedule builder, standings with the exact King Juan Cup tiebreaker order, live score entry, knockout placeholders, printable check-in sheets and referee score cards, bracket.

P0

Event comms

The lifecycle emails the current tournament runs by hand as 11 Apps Scripts — registration received, invoice, payment reminder, team confirmed, roster request/received, info packet, schedule & scores posted, announcement, see-you-today, thank-you, photos. Editable templates + rotating sponsor block, fired by event state changes.

P1

Youth Soccer Weekly

A job queries events in a date window and drafts a roundup post; you edit and publish. Turns event density into recurring content with almost no writing.

P1

Social content pipeline

Generate Event of the Week / This Weekend / Looking for Opponent / Team Feature / schedule / champion graphics + captions from event data. Export a pack; later post via Graph API.

P1

Event discussion

Polymorphic threaded comments on events, teams, and posts. Organizer pin/lock/hide, report button, batched digest notifications. Basic version ships in Phase 1.

P0-lite

Admin & moderation

Approve pending events, verify team claims, feature events, work the comment report queue. A protected route with a few tables — not a framework, just enough to run the platform.

08 — Identity

Auth & identity

Progressive login. Everything readable is public and needs no account. Login gates only actions, and the only provider is Google.

No login

  • Browse & filter events
  • View event, team, match pages
  • Read Youth Soccer Weekly & discussion threads
  • See who's looking for an opponent

Login required

  • Submit / create an event
  • Create a scrimmage, send/accept offers
  • RSVP, register a team, submit a roster
  • Claim & manage a team, upload results/photos
  • Post in a discussion, follow / favorite

Identity centers on Team, not user profile: user → team_members → team → its events, matches, results, photos. A user is just a login; the team is what has a page, a history, and a following. One user can manage several teams (a club coordinator), and a team can have several managers.

09 — First move

King Juan Cup: spreadsheet → platform

King Juan Cup 2026 runs today on a static site, a Google Sheet, and eleven Apps Scripts that publish JSON to a GitHub repo. Every one of those moving parts is a feature the platform should own. Moving the event onto the platform is both the migration and the proof that the model works.

Import path

  1. The structured data already exists: teams.json and schedule.json in github.com/sidbai/kingjuan-assets, plus the Google Sheet and the handbook / check-in / score-card PDFs. Copy them into data/king-juan-cup-2026/ in the repo.
  2. Write scripts/seed-kjc.ts that maps those files onto the schema — 1 event, 1 venue, 3 divisions, 20 teams + event_teams, rosters where known, matches with scores and placeholders, 3 sponsors, the 5v5 ruleset, champions/finalists into standings.
  3. Run it against a Neon branch, review the rendered event page and archive entry, then promote.
  4. Point kingjuancup.org at the King Juan Soccer event page (or embed it).
  5. For 2027: "Clone event" copies the ruleset, divisions, sponsors, comms templates, and venue into a new draft — the payoff for modeling it properly.
This migration is what makes tournament ops and event comms concrete. The check-in sheet, referee score card, tiebreaker order, roster rules, and the eleven email templates are a precise spec — build against real King Juan Cup data, not invented data.

Week one, in order

  1. create-next-app (TS, Tailwind, App Router). Deploy the empty shell to Vercel + register the domain.
  2. Neon project + Drizzle wired up; first migration: events, event_kinds, venues, teams, event_divisions, event_teams, rosters, matches.
  3. Pull teams.json / schedule.json from the assets repo into the fixture; write and run seed-kjc.ts.
  4. Build the read-only event detail + archive pages against that data. Nothing interactive yet.
  5. Add Auth.js + Google. Gate one action ("submit an event") to prove the pattern.

By the end of that week the King Juan Cup 2026 page is live on the real domain, and the schema and auth pattern that everything else builds on are settled.
